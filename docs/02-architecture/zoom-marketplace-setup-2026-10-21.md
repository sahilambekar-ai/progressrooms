# Zoom Marketplace setup for Progress Rooms

Updated 2026-10-21. Application implementation uses a shared mock/live provider interface. Mock identities cannot be converted to verified identities by changing an email or copying sample tokens: after live configuration, each intended teacher authorizes Zoom again. Marketplace publication and live acceptance are still separate steps.

## What you do in Zoom Marketplace

1. Sign in to [Zoom App Marketplace](https://marketplace.zoom.us/) with developer permissions. Open **Developer → Develop → Build an app → General app**. Name it **Progress Rooms** and select **User-managed**. Use one platform app; individual studios and teachers do not create S2S apps. Start with the app's **Development** credentials. [Zoom app setup](https://developers.zoom.us/docs/integrations/create/)
2. Set the OAuth redirect URL and OAuth allow list to the same exact frontend callback. For the repository's UAT deployment this is `https://uat.progressrooms.com/integrations/zoom/callback`. Enable exact/strict matching where offered. For a different environment, substitute its actual HTTPS frontend origin and tell us which one you selected. The frontend forwards the code to the authenticated backend; the callback's intended teacher must be signed into Progress Rooms. This route must be deployed before a real test.
3. Add the following **user-level granular scopes**, with these explanations. Do not select the `:admin` or `:master` versions. Recording access, Meeting SDK and Zoom Apps SDK are outside this release. [Zoom scope reference](https://developers.zoom.us/docs/integrations/oauth-scopes-granular/)

   | Scope | Description to enter |
   |---|---|
   | `user:read:user` | Verify the Zoom user ID, account ID and email of the consenting teacher. |
   | `meeting:write:meeting` | Create a scheduled class meeting owned by the consenting host. |
   | `meeting:read:meeting` | Retrieve saved meeting details and a fresh start URL for the authorized host. |
   | `meeting:read:list_meetings` | Reconcile an uncertain create response without creating duplicate meetings. |
   | `meeting:update:meeting` | Reschedule a class or explicitly apply studio defaults to future meetings. |
   | `meeting:delete:meeting` | Cancel a class meeting through its original host authorization. |

4. Under **Features → Access**, obtain the webhook **Secret Token**. Configure the **Deauthorization Notification Endpoint URL** as `https://uat.progressrooms.com/api/v1/integrations/zoom/deauthorization` (or the corresponding HTTPS API origin for your environment). If the builder exposes endpoint validation/event subscription controls, use this same endpoint for validation; no meeting-content/recording events are needed. We install the secret first, then you can complete the validation challenge. The implementation checks signed requests and timestamps and answers `endpoint.url_validation`. [Webhook configuration and verification](https://developers.zoom.us/docs/api/webhooks/)
5. Bring back the configuration in the table below. You can create the app and collect its development values before the updated UAT build is deployed. **Do not change to production credentials yet.** Once configuration is installed, use **Local Test** with two distinct permitted Zoom users. Development sharing can be restricted to your developer account; distribution to unrelated studios requires the appropriate Marketplace review/distribution approval. [Testing and distribution](https://developers.zoom.us/docs/integrations/create/)

## Values to provide afterward

| Value | Backend variable / use |
|---|---|
| Development Client ID | `ZOOM_CLIENT_ID` |
| Development Client Secret | `ZOOM_CLIENT_SECRET` |
| Webhook Secret Token | `ZOOM_WEBHOOK_SECRET` |
| Exact approved OAuth redirect URL | `ZOOM_REDIRECT_URI` |
| Environment selected (UAT or another HTTPS environment) | Confirms frontend/API origins and which credential set to install. |
| Selected scope names and any Zoom account restrictions | Confirms expected permissions and permitted test users. |

Put the Client Secret and webhook Secret Token in the backend secret configuration or an ignored, permission-restricted local file; provide the file path/variable names rather than screenshots of secrets. No studio Zoom password, Account ID for an S2S app, manually generated access token, or manually generated refresh token is required. `ZOOM_TOKEN_ENCRYPTION_KEY` is generated by Progress Rooms, is not a Zoom Marketplace value, and must remain stable across deployments.

## What happens when the real values are available

We set the backend to `ZOOM_PROVIDER_MODE=live`, install the actual values, retain the encryption key, and use `APP_ENV=production` for the deployed service. The application environment name does not mean the app must use Zoom production credentials: UAT uses live Zoom APIs with the app's **development** credentials while testing. No mock identity is treated as live-ready. Each intended teacher reconnects through OAuth and confirms the verified account; the owner then selects a live default host and enables automatic provisioning.

The authorization redirect is a frontend route, while code exchange, refresh and revocation remain backend-only. No Zoom secret belongs in a `NEXT_PUBLIC_` variable. API access is limited to the consenting user (`users/me`), and a grant cannot be actively bound to several members/studios in v1. Existing saved meeting hosts are never reassigned by changing studio defaults.

## Live acceptance after configuration

Test two distinct permitted Zoom users, one teacher using owner fallback, real host start and enrolled student join, a reschedule and cancellation, a token refresh, reconnect and explicit replacement. Verify a locked Zoom account setting is reported as restricted. Confirm the account/license restrictions observed during the test. The fallback account holder must start their meeting; no unattended start, password sharing, shared host key or automatic alternative-host privilege is promised.

Zoom documents that public-app deauthorization generates notifications, while private/development apps do not. Signed deauthorization and replay handling are tested locally; real Marketplace removal notification acceptance needs the supported published-app environment. Do not mark that gate passed because a development uninstall did not send an event. [Zoom deauthorization behavior](https://developers.zoom.us/docs/integrations/end-user-auth/)

Publishing to external studios is a later manual phase. Prepare the privacy policy, terms/support URLs, scope justifications and reviewer instructions requested by the Marketplace builder. Production credentials and any newly approved URLs replace development configuration only after the live acceptance pass. [Zoom security requirements](https://developers.zoom.us/docs/distribute/security-requirements/)
